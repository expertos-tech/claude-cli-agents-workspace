# Changelog

All notable changes to Claude CLI Agents Workspace are documented in this file. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project uses [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [0.2.0] - Unreleased

### Added

- `/merge` writes the project's `CHANGELOG.md` at every merge into `developer`, always under a named version (`## [X.Y.Z] - Unreleased`): a `feat` makes it a minor, anything else a patch, and a fix of something that entered the same unreleased version adjusts its entry instead of adding a "Fixed" one (`rules/docs.md`). With no argument, `/merge` takes the clone of the session.
- `/merge --main <project> [instructions]` releases the project: every repo in it with its own version, dated `CHANGELOG.md` and annotated tag `vX.Y.Z` (`aiwp-cmds.sh release <repo> --tag vX.Y.Z`, which never moves a tag), then the project version in its root repo, whose `CHANGELOG.md` gets a "Components" table and whose `README.md` keeps the production versions. It first states its plan and every conflict an instruction would cause (a partial release that breaks a dependency between the repos), and asks.
- Plans, requests and documents Claude writes to a file are saved in English and shown in your language.
- `/merge --main` ends with a final review of everything since the last release, widened to what the reviewer judges necessary, with the three questions of every merge review (what was asked against what was done, what went beyond the request, what existed and was lost) against every request in `qa/`, and the `CHANGELOG.md`. An unexplained change or loss stops the release.
- `scripts/check-workspace.sh --i18n-pending` (the gate of the product repository) lists missing or outdated translations as pending instead of failing.
- `/merge --hotfix <project> <description>` fixes an error in production from `main`, never from `developer`: a clone from the remote `main` (`aiwp-cmds.sh open --from-main`), only what the error needs, the gate against `main` and a review of the fix (a change unrelated to the error is a BLOCKER), your OK, then `main` by fast-forward (`aiwp-cmds.sh hotfix`), the patch version `vX.Y.(Z+1)` and its tag when you say to publish (`hotfix-tag`), and right after it `main` merged into `developer` (`hotfix-down`: a merge commit; a conflict goes through a `fix/<slug>-developer` clone and the gate). The question "publish to production with the fix?" comes before the push of a `main` that deploys by itself, after it otherwise. Each of the three commands asks for your confirmation.
- A repo whose remote `main` holds a commit its remote `developer` does not (a hotfix not merged down, after a cancel or a crash) is blocked, computed from git with no state file: the gate refuses every merge into its `developer` (except the branch that brings `main` down) and `release` refuses its release; `aiwp-project-state.sh`, `aiwp-cmds.sh open` and the warning of a message that names the project say so.

- A request lifecycle in `custom/requests/`: pending (state `idea` or `ready`), `qa/<project>/` once `/merge` takes it into `developer` (with an "Execution" block: what was done, decisions, deviations, the status of each acceptance criterion), `done/<project>/` once released. `/merge --main` validates every request waiting in `qa/<project>/` against the code, gathers every finding, and asks per finding: fix now in the release clone, or a request.
- `/run-tools`: checkboxes with the local tools of this machine (observability, the login and Safe Browsing simulators, the Azurite console, and this machine's container console: docker-ce on Linux and WSL, Colima on macOS), each with its URL and state; it starts the ones you tick and ends with a table of tool, URL and state. Unticking a tool that is up stops nothing; `/run-tools --down` stops. Behind it, `scripts/run-tools.sh` (`list --json`, `status`, `up`, `down`): a tool whose configuration is missing in `custom/` or whose port is busy is refused with the reason while the others start; each start tags the images it replaces as `<name>:rollback-latest`; a console is installed (`make install`) or its service started.
- Configurable rules: `custom/rules-config.json` turns core rules, skills and agents off (`core.<kind>.exclude`) and replaces a core rule with your own (`replace`); `custom/my-rules/` holds your own rules, skills (`skills/<name>/`) and agents (`agents/<name>.md`), each reaching the session as `custom-<name>`. The mandatory core, declared in `rules/manifest.json` (`AGENTS.md`, `rules.md`, `git.md`, `security.md`, the hooks, the deny rules, `/merge`, `/commit`, `/request`, the agents `reviewer` and `verifier`, `aiwp-cmds.sh`, `aiwp-gate.sh`, `setup-claude.sh`), always loads: a configuration that names it is ignored with a warning at the session start, and so is anything else wrong with it, never stopping a session. A rule turned off also leaves the instructions: the session reads a generated `.claude/AGENTS.md`, without it. Your own skills and agents keep only a closed list of front matter keys: no hooks, permission mode, tool grant or a model the subagent guard refuses. `scripts/rules-config.py` does the work for `setup-claude.sh` (decision record 0003).
- `/rules`: shows the rules, skills and agents a session loads and where each comes from, with the warnings; `exclude`, `include`, `replace <rule>` (copies the core rule as a starting point) and `add <subject>` change them, rebuild `.claude/` and commit in `custom/`; `lessons` proposes own rules from the lessons of `custom/docs/lessons.md` tagged `[grave]` or recurring, never `[rare]`.
- Work in a clone with no question: `guard-bash` approves a command line that stays in one clone of `tmp/work/` (its paths included) and reaches no remote system, and `setup-claude.sh` writes allow rules for edits of `tmp/work/` and the border commands of `aiwp-cmds.sh` (`open`, `status`, `push`, `up`, `down`) into `.claude/settings.json`. Leaving the clone falls back to your permission mode. A line it would ask about that holds other commands is refused with "Run it alone", so a question shows only what it approves (decision record 0004).
- A Docker copy per task: `aiwp-cmds.sh up <work>/<clone>` publishes the task's stack in its own compose group `agent_<MMDD>-<slug>` (`--<clone>` for a second clone), with its own images, on random free ports in 61000-65535 (printed, and passed as `AGENT_PORT_*` variables), never touching your stack. Its networks are internal with an isolated gateway, so a container that publishes no port reaches neither the host nor the outside; `up` refuses what its isolation needs (host networking, a Docker socket, a bind outside the clone, external networks or volumes...), naming each; a service with privileges, capabilities, devices or another key off its safe list starts with a warning, and `exec` into it follows your permission mode instead of being approved by the hook. `down` stops it; `status` lists the groups with their ports; the group is destroyed by its label at `/merge` into `developer` and at `close`. Inside the group Claude works with no question: `down -v`, `logs`, and `exec` into a container whose isolation `docker inspect` confirms.
- `/docker-deploy [developer|main]`, which only you run: updates the final stack of a project from that branch (`main` from a temporary checkout whose binds map to the project's own data), tags the replaced images for `rollback`, and never deletes a volume (`aiwp-cmds.sh deploy`, which `guard-bash` flags with a warning).
- The merge only on your order: `/merge` cannot be invoked by Claude; the `UserPromptSubmit` hook records each `/merge` you type (with its target, valid for 12 hours), and `gate --merge` refuses without one. A task ends with its tests passing, its copy published, and a closing board with the copy's addresses, one test item per acceptance criterion and the two ways out: `/merge` when approved, `close --discard` when not.
- The return review: after the fixes of a review's findings, one review focused on them (effort `high`) and one light on the whole range for regressions (effort `medium`), in parallel; a class of finding that comes back changes the approach of the fix, and a third round with a BLOCKER open stops and asks you.
- `rules/quality.md` strongly recommends a test seed to a project with a database, and `/normalize-projects` reports its absence.
- Hard rules and warnings (`rules/security.md`, decision record 0005): the hooks, the gate and the reviews refuse only a closed list (a secret committed, pushed or read; published history rewritten or a remote repository deleted; a git write in `projects/` or any write in the core outside the gate, Terraform outside `apply`; a merge without your order; a database or Grafana's data deleted without your confirmation; an irreversible change nobody asked for). Everything else is a warning, gathered and shown once, numbered (`W-1`, `W-2`...), each with what was seen, why it may be a problem, its risk (`HIGH`: it can reach the public or production, or lose data; `MEDIUM`: rework or a broken flow later; `LOW`: hygiene or quality) and a suggestion: in a warnings board that ends a wave before its closing board, and in `/merge` before it merges; both wait until you answer `fix`, `request` or `accept` for each, and the closing board's `Warnings:` line and the request's Execution block record your decisions. Also when `/draft-request` writes a request, which records what you keep as "Authorizations" so no hook, check or review asks or reports it again.
- `tools/compose.yaml`: every container tool in one compose project, `claude-cli-agents-tools`, so the container console shows them as one group. Each tool's own `compose.yaml` still starts it alone, for development, and carries an `x-run-tools` block (title, description, URL) on its main service.
- Your preferred language of communication: `aiwp new` asks it once on the terminal, right after the custom layer, by its English name (`portuguese`, `spanish`: English letters, spaces, hyphens and parentheses, at most 40; anything else is asked again), and writes it as the Claude Code setting `language` in `.claude/settings.local.json` of the workspace, keeping that file's other keys. Claude replies in it in every session, even when it runs a request file written in English; with none set (an empty answer, an install with no terminal), in the language you write in. `aiwp update` and `setup-claude.sh` never ask it and never change that file.
- `aiwp update` removes a link `~/.local/bin/single-claude` that points at the updated workspace's `scripts/single-claude.sh`, gone with the single-agent mode, and says so; nothing else in `~/.local/bin` is touched.
- `/import-workspace <folder>` brings the work of an older workspace of yours, never changing it, and never its rules: its git repositories into `projects/` (every local branch and tag, its `origin`; you choose which ones, seeing each one's size, with `skip` and `include`), the branches of its worktrees and work clones into those repositories, one pending-work request per project with uncommitted files or commits never pushed (named, to compare by hand), and its backlog as requests in state `idea` with their text unchanged, in `custom/requests/`. Behind it, `scripts/workspace-import.py` does every fact and keeps the state in `custom/migrations/import-<date>.json`; Claude only answers its questions (is this repository a project or data, which project a backlog item is about), each with its evidence, and you confirm the plan before `apply`, which resumes after a failure. It handles a workspace moved to another folder (its worktrees are paired again by their own git folders), clones of the older workspace itself (listed, not brought) and a copy with missing objects (what is complete is brought, the rest named). The import commits `custom/` and pushes nothing; `.env` files are never opened.
- `aiwp-cmds.sh bring-branch <folder> <repo> <ref> <branch>` fetches one commit of a worktree or work clone outside the workspace into a project as a new local branch, never touching either checkout and never pushing; it also takes the own git folder of a moved worktree, and refuses a ref with a missing object.
- A request in progress: `/request <file>` moves it to `custom/requests/doing/` once its clone is open (`aiwp-cmds.sh open --request <file>`, a rename committed by path in `custom/` and pushed), so no closing board, `/merge` summary or "next request" line offers it again: they name it `<file>.md in progress: <work>`. A request you wrote by hand and did not commit is scanned for secrets first and committed as it is; a secret, or a scan that cannot run (no Docker), refuses before anything is created. Running `/request` on a request in `doing/` shows its work folder, branch, last commit, files not committed, commits not on the remote and its `## Stopped` section, then asks: resume (the clone of that branch, or a new one from the remote branch, `open --resume`) or start over (`close <work> --discard --start-over`: the work folder and its remote work branches deleted, each with a lease on its last pushed sha, then a new clone of the same branch). `close <work> --discard` puts the request back in `custom/requests/`; `/merge` moves it from `doing/` to `qa/<project>/`; `aiwp-cmds.sh status` names the request of each work and lists a file of `doing/` no work records as `stale`; `/request` on a request in `doing/` also names its session. `close` now refuses an unknown option (exit 2).
- The `assisted` mode of `/pilot`, the default of a new workspace: Claude runs every check as in `auto`, and at the moments a newcomer gets the flow wrong (the first reply of a session, a new task in a long session, a commit or push on `main` or `developer`, a change straight in `projects/`, a large or vague request, a change to the core, a secret in the conversation, a refusal of a hook or the gate, the closing board) it first asks, with a short box (`ASSISTED · <group> · <title>`: What, Why, How) shown next to the options: Continue, Don't show this again (that group, until the session ends) or, where there is one, the better way. The boxes only explain: nothing is allowed or refused differently, and a subagent never shows one (`rules/assisted.md`, read only in this mode). `/pilot auto` makes `auto` your default and the boxes stop; `/pilot assisted` brings them back; `/pilot manual` stays a choice of one session. The default lives in `.claude/pilot-mode` of the workspace, never in the shared custom layer (`scripts/pilot-mode.sh`, whose three commands `setup-claude.sh` allows); the session start names the mode in one line, again after `/clear` and a compaction (`release-notice.sh`, whose entry now also runs on `clear` and `compact`). With `/pilot` turned off in `custom/rules-config.json`, every session is in `auto`. `aiwp rollback` to a version without the mode keeps `assisted` for a workspace that never chose, so the next update does not turn it to `auto`.
- `install.sh --developer` installs the unreleased product: it checks out the newest commit of the branch `developer` instead of the newest release tag (it wins over `AIWP_REF`), alone or with the workspace folder, in either order, also under `curl ... | bash -s -- --developer <folder>`; take the installer itself from `developer` (`.../developer/install.sh`), since the one on `main` predates the option. It says the installation is not a release: `aiwp update` moves it only to a release newer than its `workspace/VERSION`, never to a newer commit of `developer`; run the installer with `--developer` again to follow `developer`, or without it to go back to the newest release. `install.sh <folder> --help` now prints the help instead of a usage error.

### Changed

- `/prompt` and `/draft-prompt` are renamed `/request` and `/draft-request` (`rules/request-writing.md`); `/request` opens the work clone before the first change to a project or POC, and its default file is `tmp/request.md`. Requests live in `custom/requests/` instead of `custom/prompts/`.
- Any project layout: a folder of `projects/` at any depth may be a repo, inside another repo too; no tool refuses a layout. A clone of a nested repo is named after its path with each `/` as `--` (`billing--billing-api`).
- The prompt log moves to `logs/prompts/` at the workspace root (a new writable folder), never versioned; `prompt-log.py sync --scan` removes any secret from it. Its sources move to `custom/config/prompt-log/sources.json`.
- `/commit`, the implementer and the docs writer no longer write `CHANGELOG.md`; `/merge` does. `/commit` stages the paths before committing them, written out in the command, never in a shell variable.
- The merge review asks three questions at every merge: what was asked against what was done, what went beyond the request, what existed and was lost. Into `developer` it reads only the difference that enters, with effort `medium`; into `main` everything since the last tag, with effort `high`; a changed script is reviewed by its difference. It is the only independent review of a request (none runs during its waves), its brief carries what you authorized, and it reports BLOCKER only for a hard rule, a correctness defect, a change outside the request, a risk a mistake reaches or a proof the request requires now; the rest is a WARNING that never stops the merge.
- The gate's phase 1 refuses only failing tests, secrets (gitleaks and, moved from `vuln`, trivy's secret scanner), env files in the commits, checks that change tracked files, the scope rules of a normalization or a hotfix and a blocked repo; any other failing check of `validate.sh` (lint, `vuln`, `iac`, coverage, terraform...) is a warning in the "Warnings" section of the audit file, listed by `/merge`. `guard-bash` no longer asks before `aiwp-cmds.sh deploy`, `checkpoint`, `developer --create` and `gate --untested`: it prints a warning and your permission mode decides. A line it refuses with "Run it alone" shows the warnings of its other commands with the refusal, as a question does (a `deploy` beside a `release`, for example).
- `rules/git.md` "Waves" no longer sends a part through the gate on its own; `/request` and `/normalize-projects` end by offering `/merge` for you to type.
- `guard-bash` asks before deleting, moving or emptying Grafana's data (`tools/observability/.data`), and refuses changes to the session variables and to the `/merge` records.
- The gate of the product repository (`scripts/check-workspace.sh`, a maintenance tool) requires a `pt-BR` and an `es` translation of every `README.md` of the repository and of every page of its root `docs/`, besides the product's documents.
- The login and Safe Browsing simulators read their file from the custom layer by default (`custom/config/login-simulator/config.json`, `custom/config/safe-browsing-simulator/threats.json`) instead of the example; without it they do not start, and a missing file is never created as a folder. The example still runs with `LOGIN_SIMULATOR_CONFIG=./config/config.json` or `SAFE_BROWSING_THREATS=./config/threats.json`.
- Azurite without `AZURITE_ACCOUNT_KEY` exits at start with the reason, and the console never starts; the check moved from Compose into the container, so a tool without its key no longer stops the others of the group.
- The tools' networks keep their names (`observability`, `login-simulator`, `safe-browsing-simulator`), so other stacks still attach to them as external.
- `measure.py` says to start observability with `bash scripts/run-tools.sh up observability`.
- Your own rules move from `custom/rules/` to `custom/my-rules/`; `CLAUDE.md` imports the generated `.claude/AGENTS.md` instead of `AGENTS.md`.
- `aiwp-cmds.sh bring` only reads its source folder (no optional lock; its fsmonitor, filters and signature checks never run), accepts an empty folder at the destination (the checkout of a parent repo that tracks the new one as a gitlink), and from a folder with missing objects brings every complete branch and tag, naming the others, instead of failing.

### Removed

- The backlog (`custom/backlog/`, `templates/backlog-item.md`): an idea is a request in state `idea`.
- The single-agent mode: `single-claude` (`scripts/single-claude.sh`), `scripts/single-agent.sh`, its `/single-agent` command and plugin, `docs/single-agent.md`, and the deny rule on `SINGLE-AGENT.md` that guarded its instructions. Working alone with one agent on a target is now how the workspace works by default. **Breaking:** the `single-claude` command no longer exists.

### Fixed

- The container consoles (`tools/container-console-docker-ce`, `tools/container-console-colima`): a Compose project group opened and closed in a single frame, with its chevron swapped for another, so a click looked like nothing happened. Its chevron now rotates (right when closed, down when open) and its rows grow and shrink in height in about 200 ms; a closed group's rows stay out of the tab order and the accessibility tree. Only a click animates: the first render, the filter and the rows the live view adds or removes change at once. The chevron of the jobs panel rotates too. The menu switch is now "Animations" and turns off this motion as well as that of the data, like the system's reduced motion. Rebuild an installed console (`make install`) to get it.
- The container consoles: `make check` passed while `npm audit --audit-level=high` reported a high vulnerability, because only the type check run after it decided the result. It now fails on such a finding.

### After updating

- The `assisted` mode: a workspace that already has a project or a prompt log is updated to `auto`, so you see no boxes; run `/pilot assisted` to try them. A workspace with neither starts in `assisted`.
- Your preferred language: an existing workspace is not asked. Add `"language": "<its English name>"` (for example `"portuguese"`) to its `.claude/settings.local.json` to have Claude reply in it; change that key to switch.
- A link `~/.local/bin/single-claude` you made for the single-agent mode is removed by `aiwp update`; a copy or a link elsewhere is yours to delete.
- A task's Docker copy needs Docker Engine 28 or later; with an older one `aiwp-cmds.sh up <work>/<clone>` refuses with the reason.
- `aiwp-cmds.sh up <repo>` for your final stack is refused: use `/docker-deploy` (`aiwp-cmds.sh deploy <repo> [developer|main]`); `rollback <repo>` still returns to the previous images.
- The allow rules of the clone arrive by themselves at the next session start (`setup-claude.sh`).
- Your custom layer, in this order: `git -C custom mv prompts requests` (the requests and their archive move together); move `custom/requests/log/sources.json` to `custom/config/prompt-log/sources.json`; copy the rest of `custom/requests/log/` to `logs/prompts/` and remove it from `custom/` (`git -C custom rm -r requests/log`); turn each file of `custom/backlog/` into a request in `custom/requests/` with `**State:** idea`; commit and push `custom/`.
- Your own rules: `git -C custom mv rules my-rules`, then commit and push `custom/`. Until then `custom/rules/` is still read, with a warning at every session start.
- A project whose `CHANGELOG.md` has a plain `## [Unreleased]` section gets it named by the next `/merge` (`## [X.Y.Z] - Unreleased`); nothing to do by hand.
- The local tools: put the real files of the simulators in `custom/config/login-simulator/config.json` and `custom/config/safe-browsing-simulator/threats.json` (unless `custom/env/<tool>.env` already points to another file), then run `/run-tools`. A tool still running in its own compose project moves into `claude-cli-agents-tools` at its first start: Azurite's volume `azurite-console_azurite-data` is copied to `claude-cli-agents-tools_azurite-data` and the old one kept until you confirm its deletion. When a project's stack is attached to a tool's network (`login-simulator`, for example), `/run-tools` names it and changes nothing: stop that stack, run `/run-tools` again, and the stack attaches again at its next start.

## [0.1.0] - 2026-11-16

Initial public release.

### Added

- The installer (`install.sh`), which installs the data folder and creates the workspace, and the `aiwp` command: new workspaces with a read-only core and a manifest, a registry of installed workspaces (`aiwp list`, `aiwp forget`), `aiwp update` over every registered workspace by command only (with backup and journal), rollback and repair. Opening detects a new release and never updates.
- Rules for Claude Code sessions (`AGENTS.md`, `rules/`), with subagents and skills generated into `.claude/` by `scripts/setup-claude.sh`.
- Work in clones under `tmp/work/` and the merge gate (`/merge`, `scripts/aiwp-cmds.sh`, `scripts/aiwp-gate.sh`), with release and Terraform apply on request.
- Hooks: `guard-bash` (it also refuses `chmod`, `chown` and `git init` on the read-only core, and `aiwp update`, `rollback`, `repair`, `forget` and the opening inside a session), `guard-subagent-model`, the `Stop` check, session names, the prompt log and the release notice at session start.
- Filled `.env` files in the custom layer, `custom/env/<name>.env`, created from the `.env.example` templates of the core by `/local-env` and read by compose with `--env-file`.
- The custom layer (`custom/`) for company data, written requests, lessons and extra rules.
- Workspace projects: the marker `<!-- AI-WORKSPACE-PROJECT x.y.z -->` on line 1 of each project's and POC's `README.md` (written by `scripts/init-repo.sh`), `migrations/` with what each version asks of the projects (`migrations/0.1.0.md`), `scripts/aiwp-project-state.sh`, and a warning at every message that names a project without the marker or out of date (the `UserPromptSubmit` hook, `aiwp-cmds.sh open` and the gate), which asks to normalize it and never blocks.
- `/normalize-projects`: lists the state of the projects, or brings a project or POC into the workspace (`--from` a URL or a folder): four Opus analysts and a plan in `custom/migrations/` that the person approves with the language of the documentation; then checkpoint tags pushed before any change, a tested branch `feat/ai-workspace-migration` with the complete documentation and `AI-WORKSPACE-MIGRATION.md`, `/merge` into `developer` and the release of `main` (a pull request when `main` is protected). New `aiwp-cmds.sh` commands `developer`, `checkpoint` and `bring`; the gate judges a normalization on what it adds; `custom/claude-md-excludes.txt` keeps a team's instruction files out of the sessions.
- Validation tools in Docker (`scripts/validate.sh`) and the product gate (`scripts/check-workspace.sh`).
- Request writing (`/draft-prompt`, `/prompt`, `templates/request.md`), the single-agent mode and performance measurement.
- Local tools in `tools/`, with your own tools in the custom layer (`custom/tools/`): observability, container consoles, login and Safe Browsing simulators (their real configuration lives in `custom/config/<tool>/`), Azurite console, usage report and Fable alert.
