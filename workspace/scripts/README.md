# scripts/

Catalog of the workspace scripts. Rules: `rules/scripts.md`. Check this list before writing a long command.
Run as `bash scripts/<name>.sh`. Each script prints its full reference with `--help`: this page only says what exists.
In an installed workspace the scripts never write in the core: their output goes to `custom/`, `projects/`, `tmp/`, `logs/`, `.history/` or a tool output folder (`bash scripts/aiwp.sh _writable` lists them).

## Validation

| Script | Does | Example |
| --- | --- | --- |
| `validate.sh` | Runs the validation tools of `docker/compose.yaml` in Docker and prints PASS/FAIL per check: `secrets`, `vuln`, `iac`, `shell`, `dockerfile`, `markdown`, `mermaid`, `terraform`, `python`, `typescript`, `coverage` (and `cost`). The `secrets` check also fails when git tracks a `.env` or a `local.settings.json`. Compose reads `custom/env/docker.env` (else the defaults of `docker/.env.example`) and mounts the workspace read-only | `bash scripts/validate.sh --path projects/billing --only secrets,markdown` |
| `aiwp-cmds.sh` | Work area: `open` a clone of a project (or of `custom/`, for a POC) in `tmp/work/<work>/`, on the branch of the request (with `--from-main`, a hotfix branch from the remote `main`), pushed at every commit after a secret scan of the commits; `run`, `status` (with the Docker copy groups of each clone and their ports), `push`, `close` (destroys the work's copy groups); `up <work>/<clone>` publishes the task's copy in its own `agent_<MMDD>-<slug>` group, on random free ports in 61000-65535 set in an override file outside the clone (`AGENT_PORT_<SERVICE>_<PORT>` variables), on internal networks only but `<group>_edge` for a service that publishes a port (a service with a key off the safe list starts with a warning and gets no auto-allow of `exec`; what the isolation needs is still refused), `down` stops it; `deploy <repo> [developer\|main]` updates the final stack (`/docker-deploy`) with a rollback tag first, `rollback` returns to it. Its `_stop-check` is the `Stop` hook | `bash scripts/aiwp-cmds.sh --help` |
| `aiwp-gate.sh` | The only ways into `projects/`, called through `aiwp-cmds.sh`: `gate` (phase 1: updated base, full tests, `validate.sh`, env files and secrets, the audit of what leaves the base; only the hard rules refuse (secrets, env files, a failing test command, checks that change tracked files, the normalization and hotfix scope rules), every other failing check of `validate.sh` is a warning under "Warnings" of the audit; phase 2 `--merge`: fast-forward of the checked sha, inside Claude Code only after a `/merge` the person typed in the session, newer than its last merge and than 12 hours, for the work or project it named, one `/merge` per work; then the clone's Docker copy groups are destroyed; a normalization branch is judged on what it adds), `release` (`developer` to `main`, and with `--tag vX.Y.Z` the annotated release tag, never moved; a pull request when `main` is protected; refused while a hotfix is not merged down), `hotfix` (the checked sha of a hotfix clone into `main` by fast-forward), `hotfix-tag` (its annotated patch tag), `hotfix-down` (`main` merged into `developer`; a conflict changes nothing and points to a resolution clone), `apply` (Terraform plan from `main`, then apply of that plan), and the steps of `/normalize-projects`: `developer`, `checkpoint` (the annotated tags, pushed) and `bring` (`--from`) | `bash scripts/aiwp-gate.sh --help` |
| `check-workspace.sh` | Gate of the product repository, a maintenance tool (in an installed workspace it prints one line and exits 2), for the checkout that holds it (only the product folder, when it sits in a subfolder of its git repo): unique decision numbers, no term of the terms list (`AIWP_TERMS_FILE`, else `custom/core-terms.txt`) in the repo, every document translated (`i18n`, only when the repository root holds `i18n/`), valid `rules/agents/settings.json`, POC files that parse, `validate.sh` on the changed files, and the script suites whose inputs changed | `bash scripts/check-workspace.sh` |
| `check-ledger.sh` | Library sourced by the two scripts above: records each PASS under a hash of its inputs, so a check runs once per state of the code (`CACHED <check>`). Not run by hand | — |
| `heavy-run.sh` | Runs a task heavy on CPU or GPU (graphics, 3D rendering): at once under 88 °C, else once the hotter of CPU and GPU reads 85 °C or less; no queue (`rules/machine-load.md`). Exit 75: still hot after 30 minutes, nothing ran | `bash scripts/heavy-run.sh -- <render command>` |
| `performance/measure.py` | Measures the workspace from the session transcripts (process, validation and gate, questions, context, time to the first edit) and writes `custom/performance/<date>-<name>.md`, compared with the previous report and the last five. Runs only with the observability stack up | `python3 -I -B scripts/performance/measure.py --name <name>` |
| `prompt-log.py` | Records every human prompt from the session transcripts (the workspace root plus the folders of `custom/config/prompt-log/sources.json`) in `logs/prompts/<project>/<year>-W<week>.md`, with the agent commits and gate merges that followed, and day and week summaries built from that data. Only adds: an expired transcript keeps its records. `--context` is a `SessionStart` hook (prints the last day with activity, never fails the session); `--scan` runs gitleaks in Docker on every week file and removes what it finds; `logs/` is not a repository, so nothing is committed or pushed | `python3 -I -B scripts/prompt-log.py sync --scan` |
| `sonar.sh` | Optional SonarQube stack (`up`, `down`, `status`, `scan`), only when the human asks. Reads `custom/env/docker-sonar.env`; the scan mounts the folder read-only and keeps `.scannerwork` in the container's `/tmp` | `bash scripts/sonar.sh scan --key billing --path projects/billing` |

## Hooks

Wired in `rules/agents/settings.json`. Each reads the hook JSON on stdin.

| Script | Does |
| --- | --- |
| `guard-bash.sh` (+ `guard-bash.py`) | `PreToolUse` on `Bash`. Denies git writes in `projects/` and the core, Terraform changes, `push --no-verify`, and a `custom/` commit carrying a secret. In an installed workspace it also denies `chmod`, `chown`, `chgrp`, `git init` and `git clone` that reach the read-only core (links, globs, `-R`, `find`, `xargs`, `sudo`, `bash -c` followed; the writable paths come from `aiwp.sh _writable`, and if that fails it asks), and `aiwp update`, `rollback`, `repair`, `forget` and the opening (`aiwp` alone, `aiwp -- ...`) inside a session. Denies a way around the person's merge order: changing `CLAUDECODE` or `CLAUDE_CODE_SESSION_ID`, writing `.history/merge-orders/`, naming `session-title.py` in any spelling. Asks before deleting a database (not in the task's own Docker group), before deleting, moving or emptying Grafana's data (`tools/observability/.data`, wherever it runs), and before `aiwp-cmds.sh release`, `hotfix`, `hotfix-tag`, `hotfix-down`, `apply --apply` and `close --discard`; `deploy`, `checkpoint`, `developer --create` and `gate --untested` print a warning and the permission mode decides; a line that would ask and holds other commands too is refused with "Run it alone", so the question shows only that command (a leading `cd` travels with it). Allows with no question a line it can tell stays in one clone of `tmp/work/<yyyy-mm-dd>-<slug>/<clone>/` (every command runs there, every path it names stays there and is no `.env`, nothing deletes its `.git`, nothing reaches a remote system or installs outside it; Docker only in the task's own group `agent_<MMDD>-<slug>[--<clone>]`: an allowlist of `docker compose` subcommands (no `up`, `build` or `run`: the copy starts only by `aiwp-cmds.sh up`), `exec` only into a container that `docker inspect` shows on internal networks of the group with an isolated gateway, not privileged, with its own namespaces, no devices, no security option but `no-new-privileges`, and only volumes of the group or binds inside the clone (no `config`: it prints env files), its resources told by their compose label; never SQL clients on the host or the workspace scripts), after every deny and ask; what it cannot tell stays silent. Reads the line the way a shell groups it; `--help` lists everything and what it does not see. An internal error asks, never passes silently |
| `release-notice.sh` | `SessionStart`: in an installed workspace, runs `aiwp.sh check --quiet` (one answer per day, bounded time, offline-safe) and, when a newer release exists, adds to the session context that Claude tells you to close the session and run `aiwp update` in a terminal. Detection only; silent otherwise |
| `guard-subagent-model.sh` (+ `guard-subagent-model.py`) | `PreToolUse` on `Agent`. Denies a fork and a model outside the allowed list, asks on Fable, sets `opus` on a call that would inherit. A failure blocks the call |

## Setup and repos

| Script | Does | Example |
| --- | --- | --- |
| `aiwp.sh` | The `aiwp` command (`~/.local/bin/aiwp` links to the copy in the data folder): `new` creates a workspace (the core read-only, a manifest, `custom/`) and registers it in `workspaces.json` of the data folder; no command opens it (release check that only says when a release exists, `setup-claude.sh`, `claude`); `list` and `forget` show and edit the registry; `update` lists the registered workspaces and updates all, the chosen ones, one folder (`<folder>`) or every one (`--all`, `--force`), by command and in a terminal only; `rollback`, `repair`, `check`, `version`. Inside a session it refuses `update`, `rollback`, `repair`, `forget` and the opening. The writable folders of an installed workspace are listed once, at its top; `aiwp.sh _writable` prints them for `guard-bash` | `aiwp new ~/my-workspace` |
| `setup-claude.sh` | Creates or syncs the git-ignored `.claude/` from `rules/agents/`, `rules/skills/` and the `rules/*.md` that carry a `paths:` front matter, with the rules configuration applied (`rules-config.py`): the effective `.claude/AGENTS.md` that `CLAUDE.md` imports, the core items `custom/rules-config.json` turns off left out, the own rules, skills and agents of `custom/my-rules/` as `custom-*`, the paths of `custom/claude-md-excludes.txt` in `claudeMdExcludes`, and the core allow rules (edits in `tmp/work/`, the `aiwp-cmds.sh` commands `open`, `status`, `push`, `up`, `down`) in `permissions.allow`, which no configuration removes; a configuration that cannot be used loads the whole core with a warning; installs the Fable alert once; when `custom/` is missing, asks for its git repo (`--custom-repo <url>`). A `SessionStart` hook runs it with `--quiet`; `--check` only reports | `bash scripts/setup-claude.sh --check` |
| `rules-config.py` | The rules configuration of the custom layer: `custom/rules-config.json` turns core rules, skills and agents off and replaces a core rule with an own one of `custom/my-rules/`; the mandatory core of `rules/manifest.json` always loads. `build` is what `setup-claude.sh` syncs; `show`, `exclude`, `include`, `replace`, `add` and `lessons` serve `/rules`. Every problem is a warning, never a failure of the session | `python3 -I -B scripts/rules-config.py show` |
| `session-title.py` | `UserPromptSubmit` hook: on `/request <file>`, names the session `<project>-<n>` from the file's `**Project:**` line, `<n>` one more than the highest of that project among the running sessions of the workspace. On every message that names a project of `projects/` or a POC (folder name, path, `**Project:**` line; a path names its nearest repo, nested ones included), adds its state to the context when it has no marker or is out of date, so Claude warns and asks to run `/normalize-projects`, and when a hotfix on `main` is not merged into `developer` yet. Records each `/merge` the person types (typed or in its expanded form) in `.history/merge-orders/<session id>`, with its target (`<work>[/<clone>]`, `--main` or `--hotfix <project>`), the order phase 2 of the gate needs; never blocks, bounded time, silent on errors | — (hook) |
| `aiwp-project-state.sh` | Prints whether each project and POC is a workspace project: the marker on line 1 of its `README.md` (of `developer`, read with `git show`) against `VERSION` and `migrations/`: no marker, up to date, out of date with the pending migrations, or the workspace's own repository; and whether a hotfix on `main` is not merged into `developer` yet (from the remote-tracking refs, no fetch). Read only; used by the hook, `aiwp-cmds.sh open`, the gate and `/normalize-projects` | `bash scripts/aiwp-project-state.sh billing-api` |
| `init-repo.sh` | Creates a project in `projects/` as an independent git repo, or a POC (`custom/pocs/`) or a tool of yours (`custom/tools/`) in the custom layer, the README of a project or POC starting with the marker of the workspace version; never writes in the core. Never overwrites | `bash scripts/init-repo.sh --type project --name billing-api` |
| `sync-env.sh` | Creates or completes the filled `.env` from a folder's `.env.example`, printing key names only: `custom/env/<name>.env` (mode 600) for `docker`, `docker/sonar` and `tools/<name>`, adding `env/` to `custom/.gitignore` when missing; `<dir>/.env` for a project or clone. Behind `/local-env` | `bash scripts/sync-env.sh --path docker` |
| `run-tools.sh` (+ `run-tools.py`) | The local tools: `list --json` and `status` show the tools of this machine (the container tools of `tools/compose.yaml`, with the `x-run-tools` block of each, and the container console of this machine: docker-ce on Linux and WSL, Colima on macOS), their state and what keeps each from starting (configuration missing in `custom/`, or in the folder `AIWP_CUSTOM_DIR` names; a busy port); `up` refuses those, tags the images it replaces as `rollback-latest`, moves a tool still in its old compose project into the group `claude-cli-agents-tools` (copying a named volume, keeping the old one), and starts the rest with `docker compose up -d --build --wait`, or the console service; `down` only stops. Behind `/run-tools` | `bash scripts/run-tools.sh up observability` |
| `agent-copy.py` | The Docker copy of a task, behind `aiwp-cmds.sh` `up`, `down`, `status`, `close` and the gate's merge: writes the override file of a copy (own images, no fixed names, random free ports in 61000-65535), lists the `agent_` groups, and destroys a group only by its compose label and only when its name matches `^agent_[0-9]{4}-[a-z0-9][a-z0-9-]*$` | `python3 -I scripts/agent-copy.py list` |
| `lib/env.sh` | Library: where the filled `.env` of a core folder lives and which file compose reads with `--env-file`. Sourced by `sync-env.sh`, `sonar.sh` and `validate.sh` | — |
| `lib/projects.sh` | Library: the layout of `projects/` (which folder is a repo). Sourced by `init-repo.sh`, `history.sh`, `aiwp-project-state.sh` and `aiwp-gate.sh` | — |

## Optional

| Script | Does |
| --- | --- |
| `history.sh` | Adds an entry to the `history.txt` of a project, of a tool of yours (`custom/tools/<name>`) or of a POC, or shows the last ones (`add`, `flush`, `show`); never in the core. No rule asks for history entries; `single-agent.sh import-history` uses it to bring a single-agent session's entries into its target |
| `single-claude.sh` | Run by the human, from a terminal: opens Claude in a project, a tool of yours or a POC folder without the workspace's instructions, hooks and skills (guide in `docs/single-agent.md`) |
| `single-agent.sh` | Support of that mode: target validation, the generated `SINGLE-AGENT.md`, its session names, `import-history` |

## Tests

Each suite runs alone, on throwaway folders: `bash scripts/tests/<name>/test-<name>.sh`. The Python tests (`scripts/tests/test_*.py`) run under the coverage gate: `bash scripts/validate.sh --only coverage`.

| Suite | Covers |
| --- | --- |
| `tests/check-workspace/` | `check-workspace.sh`, the ledger, and the argument handling and tracked-secret check of `validate.sh` |
| `tests/aiwp-cmds/`, `tests/test_agent_copy.py` | `aiwp-cmds.sh` and `agent-copy.py`: clones, automatic push, pre-push refusals, Stop hook, close, the task's copy (`up`, `down`, `status`, destruction by label) with a fake docker and, when Docker and `alpine:3.20` are on the machine, one real copy beside a final stack it never touches; `deploy` and `rollback` |
| `tests/aiwp-gate/` | `aiwp-gate.sh`: both gate phases, the person's `/merge` that phase 2 needs inside Claude Code (its target, its 12-hour limit), the copy groups destroyed after the merge, base that moved, conflicts, the audit, release (a protected `main` and its pull request, the `--tag` cases), the hotfix (from `main`, into `main`, its tag, the merge down, clean and with a conflict, and the blocked repo), apply, and the normalization steps against local bare remotes: `developer`, the checkpoint tags, `bring`, the gate that judges what the branch adds |
| `tests/guard-bash/`, `tests/test_guard_bash.py` | `guard-bash.sh` and `guard-bash.py` |
| `tests/guard-subagent-model/`, `tests/test_guard_subagent_model.py` | `guard-subagent-model.sh` and `guard-subagent-model.py` |
| `tests/setup-claude/`, `tests/test_rules_config.py` | `setup-claude.sh` and `rules-config.py` |
| `tests/aiwp/` | `aiwp.sh`, the root `install.sh` and `release-notice.sh`, offline, on a fixture repository with two releases |
| `tests/sync-env/` | `sync-env.sh` and `lib/env.sh` |
| `tests/run-tools/`, `tests/test_run_tools.py` | `run-tools.sh` and `run-tools.py`, with fake docker, uname, systemctl, launchctl and make |
| `tests/heavy-run/` | `heavy-run.sh` |
| `tests/single-agent/` | `single-agent.sh` and `single-claude.sh` |
| `tests/test-projects-layout.sh` | `init-repo.sh` (the marker included), `history.sh`, `lib/projects.sh` |
| `tests/aiwp-project-state/` | `aiwp-project-state.sh`: no marker, equal, older with and without a newer migration, README without marker, POC, the workspace's own repository |

A new suite is added to `SUITES` and `suite_inputs` of `check-workspace.sh`.
