# 0.1.0

The first normalization: it brings a project or a POC that has no marker into the workspace. `/normalize-projects`
applies it in two stages, with the person's approval between them. Nothing in it rewrites the project's code.

## Stage 1: analysis

A deep analysis of the whole repository, by four analysts that read a fresh clone of `developer` and change nothing.
No fixed list of file or folder names decides anything: each piece is judged by what it does.

1. **Instructions:** what tells an AI tool or a person how to work here (instruction files, prompts, rules, skills,
   agents, editor or assistant settings, process documents); whether each piece is still true, competes with the
   workspace rules, or is used by a team on other tools.
2. **Company and environment:** what belongs to the company or the machine rather than to the code: tenant,
   subscription, internal URLs, people, customer names, deployment environments, secret-shaped values.
3. **Build and test:** how the project is built, run and tested today; what it needs (runtimes, `.env`, services);
   whether the suite passes.
4. **Conformity:** what falls short of the project contract below.

The findings become a migration plan in `custom/migrations/<repo>-<yyyy-mm-dd>.md`, one line per finding, each with a
destination: the custom layer, stays in the project, changes in the project, gap (reported only) or security alert
(reported only). The person approves, edits or drops each line and chooses the language of the documentation.

## Stage 2: migration

1. `projects/<repo>` on `developer`, with `developer` on the remote.
2. Annotated checkpoint tags on the current heads, pushed: `ai-workspace-migration/<yyyy-mm-dd>/developer` and
   `ai-workspace-migration/<yyyy-mm-dd>/main`.
3. A clone on `feat/ai-workspace-migration`, from `developer`.
4. The approved plan, in commits:
   - company- and environment-specific knowledge to the custom layer, as a rule scoped to the project's paths, never
     with a secret value;
   - instruction files whose content moved are removed (a team repository may keep them, excluded in the workspace
     only, through `custom/claude-md-excludes.txt`);
   - the complete documentation, in the chosen language: overview, architecture, setup and run (the variables of
     `.env.example`, never values), configuration, tests, deployment, operations; existing docs reviewed, fixed and
     completed; the `README.md` links to it and has a "How to test" section;
   - `.env` files ignored by git;
   - `AI-WORKSPACE-MIGRATION.md` at the project root: what changed, the documentation and its language, the gaps
     (missing tests, coverage, off-standard code or architecture, dependencies), the result of the branch test, and
     only the count of security alerts;
   - last, the marker `<!-- AI-WORKSPACE-PROJECT 0.1.0 -->` on line 1 of `README.md`.
5. The branch tested with the person; then `/merge` into `developer` and `aiwp-cmds.sh release` into `main`.
6. The project's line in `custom/projects.md`, with the documentation language.

A POC gets the same analysis and approval; its changes are commits in `custom/`, with no branch, tag, gate or
release.

## Project contract

- `README.md` with the marker on line 1, what the project is, how to run it and a "How to test" section with the full
  test command (the gate runs it).
- The complete documentation, linked from the `README.md`.
- A `developer` branch on the remote; `main` moves only by release.
- `.env` and other local secret files ignored by git; `.env.example` with the variable names and no values.
- No instruction file that competes with the workspace rules, unless kept for a team and excluded in the workspace.

## Check

- `bash scripts/aiwp-project-state.sh <repo>` prints `up to date (marker 0.1.0, ...)`.
- The checkpoint tags, `feat/ai-workspace-migration`, `developer` and `main` are on the remote, and `developer` and
  `main` hold the marker.
