# scripts/

Catálogo dos scripts do workspace. Regras: `rules/scripts.md`. Consulte esta lista antes de escrever um comando longo.
Rode como `bash scripts/<name>.sh`. Cada script mostra a referência completa com `--help`: esta página só diz o que existe.
Num workspace instalado, os scripts nunca escrevem no core: a saída deles vai para `custom/`, `projects/`, `tmp/`, `logs/`, `.history/` ou a pasta de saída de uma ferramenta (`bash scripts/aiwp.sh _writable` as lista).

## Validação

| Script | Faz | Exemplo |
| --- | --- | --- |
| `validate.sh` | Roda em Docker as ferramentas de validação de `docker/compose.yaml` e mostra PASS/FAIL por check: `secrets`, `vuln`, `iac`, `shell`, `dockerfile`, `markdown`, `mermaid`, `terraform`, `python`, `typescript`, `coverage` (e `cost`). O check `secrets` também falha quando o git rastreia um `.env` ou um `local.settings.json`. O compose lê `custom/env/docker.env` (senão, os padrões de `docker/.env.example`) e monta o workspace só leitura | `bash scripts/validate.sh --path projects/billing --only secrets,markdown` |
| `aiwp-cmds.sh` | Área de trabalho: `open` abre um clone de um projeto (ou do `custom/`, para uma POC) em `tmp/work/<work>/`, na branch do pedido (com `--from-main`, uma branch de hotfix a partir da `main` do remoto), com push a cada commit depois de uma varredura de segredos dos commits; `run`, `status` (com os grupos da cópia Docker de cada clone e as portas deles), `push`, `close` (destrói os grupos de cópia do trabalho); `up <work>/<clone>` publica a cópia da tarefa no próprio grupo `agent_<MMDD>-<slug>`, em portas livres aleatórias de 61000-65535 definidas num arquivo de override fora do clone (variáveis `AGENT_PORT_<SERVICE>_<PORT>`), só em redes internas, exceto `<group>_edge` para um serviço que publica uma porta (um serviço com uma chave fora da lista segura inicia com um aviso e não ganha o auto-allow do `exec`; o que o isolamento exige continua recusado), `down` a para; `deploy <repo> [developer\|main]` atualiza a stack final (`/docker-deploy`) com uma tag de rollback antes, `rollback` volta para ela. O `_stop-check` dele é o hook `Stop` | `bash scripts/aiwp-cmds.sh --help` |
| `aiwp-gate.sh` | Os únicos caminhos para `projects/`, chamados pelo `aiwp-cmds.sh`: `gate` (fase 1: base atualizada, testes completos, `validate.sh`, arquivos de env e segredos, a auditoria do que sai da base; só as hard rules recusam (segredos, arquivos de env, um comando de teste que falha, checks que alteram arquivos rastreados, as regras de escopo da normalização e do hotfix), qualquer outro check do `validate.sh` que falhe é um aviso em "Warnings" da auditoria; fase 2 `--merge`: fast-forward do sha verificado, dentro do Claude Code só depois de um `/merge` que a pessoa digitou na sessão, mais novo que o último merge dela e que 12 horas, para o trabalho ou projeto que ela nomeou, um `/merge` por trabalho; depois os grupos de cópia Docker do clone são destruídos; uma branch de normalização é julgada pelo que ela acrescenta), `release` (`developer` para `main` e, com `--tag vX.Y.Z`, a tag anotada do release, nunca movida; um pull request quando a `main` é protegida; recusado enquanto um hotfix não foi mesclado de volta), `hotfix` (o sha verificado de um clone de hotfix para a `main` por fast-forward), `hotfix-tag` (a tag anotada de patch dele), `hotfix-down` (a `main` mesclada na `developer`; um conflito não altera nada e aponta para um clone de resolução), `apply` (plano do Terraform a partir da `main`, depois o apply desse plano) e os passos do `/normalize-projects`: `developer`, `checkpoint` (as tags anotadas, enviadas) e `bring` (`--from`) | `bash scripts/aiwp-gate.sh --help` |
| `check-workspace.sh` | Gate do repositório do produto, uma ferramenta de manutenção (num workspace instalado ele imprime uma linha e sai com 2), para o checkout que o contém (só a pasta do produto, quando ela fica numa subpasta do repositório git dela): números de decisão únicos, nenhum termo da lista de termos (`AIWP_TERMS_FILE`, senão `custom/core-terms.txt`) no repositório, todo documento traduzido (`i18n`, só quando a raiz do repositório tem `i18n/`), `rules/agents/settings.json` válido, arquivos de POC que fazem parse, `validate.sh` nos arquivos alterados e as suítes de scripts cujas entradas mudaram | `bash scripts/check-workspace.sh` |
| `check-ledger.sh` | Biblioteca carregada pelos dois scripts acima: registra cada PASS sob um hash das entradas dele, para que um check rode uma vez por estado do código (`CACHED <check>`). Não se roda à mão | — |
| `heavy-run.sh` | Roda uma tarefa pesada de CPU ou GPU (gráficos, renderização 3D): na hora abaixo de 88 °C, senão quando o mais quente entre CPU e GPU marcar 85 °C ou menos; sem fila (`rules/machine-load.md`). Saída 75: ainda quente depois de 30 minutos, nada rodou | `bash scripts/heavy-run.sh -- <render command>` |
| `performance/measure.py` | Mede o workspace a partir dos transcripts das sessões (processo, validação e gate, perguntas, contexto, tempo até a primeira edição) e grava `custom/performance/<date>-<name>.md`, comparado com o relatório anterior e com os últimos cinco. Só roda com a stack de observabilidade no ar | `python3 -I -B scripts/performance/measure.py --name <name>` |
| `prompt-log.py` | Registra todo prompt humano dos transcripts das sessões (a raiz do workspace mais as pastas de `custom/config/prompt-log/sources.json`) em `logs/prompts/<project>/<year>-W<week>.md`, com os commits de agente e os merges do gate que vieram depois, e resumos de dia e de semana montados a partir desses dados. Só acrescenta: um transcript expirado mantém os registros. `--context` é um hook `SessionStart` (mostra o último dia com atividade, nunca derruba a sessão); `--scan` roda o gitleaks em Docker em todo arquivo de semana e remove o que encontrar; `logs/` não é um repositório, então nada é commitado nem enviado | `python3 -I -B scripts/prompt-log.py sync --scan` |
| `sonar.sh` | Stack opcional do SonarQube (`up`, `down`, `status`, `scan`), só quando o humano pede. Lê `custom/env/docker-sonar.env`; o scan monta a pasta só leitura e mantém o `.scannerwork` no `/tmp` do contêiner | `bash scripts/sonar.sh scan --key billing --path projects/billing` |

## Hooks

Ligados em `rules/agents/settings.json`. Cada um lê o JSON do hook na stdin.

| Script | Faz |
| --- | --- |
| `guard-bash.sh` (+ `guard-bash.py`) | `PreToolUse` em `Bash`. Recusa escrita git em `projects/` e no core, mudanças de Terraform, `push --no-verify` e um commit no `custom/` que leva um segredo. Num workspace instalado, também recusa `chmod`, `chown`, `chgrp`, `git init` e `git clone` que chegam ao core só leitura (links, globs, `-R`, `find`, `xargs`, `sudo` e `bash -c` são seguidos; os caminhos graváveis vêm de `aiwp.sh _writable`, e se isso falhar ele pergunta), e `aiwp update`, `rollback`, `repair`, `forget` e a abertura (`aiwp` sozinho, `aiwp -- ...`) dentro de uma sessão. Recusa um jeito de contornar a ordem de merge da pessoa: mudar `CLAUDECODE` ou `CLAUDE_CODE_SESSION_ID`, escrever em `.history/merge-orders/`, citar `session-title.py` em qualquer grafia. Pergunta antes de apagar um banco de dados (não no grupo Docker da própria tarefa), antes de apagar, mover ou esvaziar os dados do Grafana (`tools/observability/.data`, onde quer que rode) e antes de `aiwp-cmds.sh release`, `hotfix`, `hotfix-tag`, `hotfix-down`, `apply --apply` e `close --discard`; `deploy`, `checkpoint`, `developer --create` e `gate --untested` imprimem um aviso e o modo de permissão decide; uma linha que perguntaria e que contém também outros comandos é recusada com "Run it alone", para que a pergunta mostre só aquele comando (um `cd` inicial vai junto com ele). Permite sem perguntar uma linha que ele consegue dizer que fica dentro de um só clone de `tmp/work/<yyyy-mm-dd>-<slug>/<clone>/` (todo comando roda ali, todo caminho que ele cita fica ali e não é um `.env`, nada apaga o `.git` dele, nada alcança um sistema remoto nem instala fora dele; Docker só no grupo da própria tarefa `agent_<MMDD>-<slug>[--<clone>]`: uma allowlist de subcomandos de `docker compose` (sem `up`, `build` ou `run`: a cópia só inicia por `aiwp-cmds.sh up`), `exec` só num contêiner que o `docker inspect` mostra em redes internas do grupo com um gateway isolado, sem privilégio, com namespaces próprios, sem dispositivos, sem opção de segurança além de `no-new-privileges`, só volumes do grupo ou binds dentro do clone, e o label `com.aiwp.copy.safe=true` que o `up` põe num serviço para o qual não imprimiu aviso (sem `config`: ele imprime arquivos de env), os recursos dele identificados pelo label do compose; nunca clientes SQL no host nem os scripts do workspace), depois de todo deny e ask; o que ele não consegue dizer fica em silêncio. Lê a linha do jeito que um shell a agrupa; o `--help` lista tudo e o que ele não vê. Um erro interno pergunta, nunca passa calado |
| `release-notice.sh` | `SessionStart`: num workspace instalado, roda `aiwp.sh check --quiet` (uma resposta por dia, tempo limitado, seguro offline) e, quando há release mais nova, acrescenta ao contexto da sessão que o Claude avisa para você fechar a sessão e rodar `aiwp update` num terminal. Só detecta; fora isso, silencioso |
| `guard-subagent-model.sh` (+ `guard-subagent-model.py`) | `PreToolUse` em `Agent`. Nega um fork e um modelo fora da lista permitida, pergunta no Fable, define `opus` numa chamada que herdaria o modelo. Uma falha bloqueia a chamada |

## Setup e repositórios

| Script | Faz | Exemplo |
| --- | --- | --- |
| `aiwp.sh` | O comando `aiwp` (`~/.local/bin/aiwp` aponta para a cópia na pasta de dados): `new` cria um workspace (o core somente leitura, um manifesto, `custom/`) e o registra no `workspaces.json` da pasta de dados e, num terminal, pergunta uma vez o idioma preferido de comunicação com o Claude (o nome em inglês: `portuguese`, `spanish`; uma resposta inválida é perguntada de novo), gravado como a configuração nativa `language` em `.claude/settings.local.json`, mantendo as outras chaves dele (uma resposta vazia ou a falta de terminal não grava nada; `update`, a abertura e o `setup-claude.sh` nunca o perguntam nem mudam esse arquivo); sem comando ele abre o workspace (checagem de release que só avisa quando há uma, `setup-claude.sh`, `claude`); `list` e `forget` mostram e editam o registro; `update` lista os workspaces registrados e atualiza todos, os escolhidos, uma pasta (`<pasta>`) ou cada um (`--all`, `--force`), só por comando e num terminal, e depois de atualizar um workspace remove, com uma linha, um link `~/.local/bin/single-claude` para o `scripts/single-claude.sh` dele, que se foi com o modo single-agent (nada mais em `~/.local/bin` é tocado); `rollback`, `repair`, `check`, `version`. Numa sessão ele recusa `update`, `rollback`, `repair`, `forget` e a abertura. As pastas graváveis de um workspace instalado estão listadas uma vez, no topo dele; o `aiwp.sh _writable` as imprime para o `guard-bash` | `aiwp new ~/my-workspace` |
| `setup-claude.sh` | Cria ou sincroniza a `.claude/` ignorada pelo git a partir de `rules/agents/`, `rules/skills/` e das `rules/*.md` que têm front matter `paths:`, com a configuração de regras aplicada (`rules-config.py`): o `.claude/AGENTS.md` efetivo que o `CLAUDE.md` importa, os itens do core que o `custom/rules-config.json` desliga deixados de fora, as regras, skills e agentes próprios de `custom/my-rules/` como `custom-*`, os caminhos de `custom/claude-md-excludes.txt` em `claudeMdExcludes`, e as regras allow do core (edições em `tmp/work/`, os comandos `open`, `status`, `push`, `up`, `down` do `aiwp-cmds.sh`) em `permissions.allow`, que nenhuma configuração remove; uma configuração que não pode ser usada carrega o core inteiro com um aviso; instala o alerta de Fable uma vez; quando falta o `custom/`, pergunta o repositório git dele (`--custom-repo <url>`). Um hook `SessionStart` o roda com `--quiet`; `--check` só relata | `bash scripts/setup-claude.sh --check` |
| `rules-config.py` | A configuração de regras da camada custom: o `custom/rules-config.json` desliga regras, skills e agentes do core e substitui uma regra do core por uma própria de `custom/my-rules/`; o core obrigatório de `rules/manifest.json` sempre carrega. `build` é o que o `setup-claude.sh` sincroniza; `show`, `exclude`, `include`, `replace`, `add` e `lessons` servem o `/rules`. Todo problema é um aviso, nunca uma falha da sessão | `python3 -I -B scripts/rules-config.py show` |
| `session-title.py` | Hook `UserPromptSubmit`: no `/request <file>`, dá à sessão o nome `<project>-<n>` pela linha `**Project:**` do arquivo, com `<n>` um a mais que o maior daquele projeto entre as sessões do workspace em execução. Em toda mensagem que cita um projeto de `projects/` ou uma POC (nome da pasta, caminho, linha `**Project:**`; um caminho cita o repo mais próximo, inclusive os aninhados), acrescenta o estado dele ao contexto quando não tem marcador ou está desatualizado, para o Claude avisar e pedir para rodar `/normalize-projects`, e quando um hotfix na `main` ainda não foi mesclado na `developer`. Registra cada `/merge` que a pessoa digita (digitado ou na forma expandida) em `.history/merge-orders/<session id>`, com o alvo dele (`<work>[/<clone>]`, `--main` ou `--hotfix <project>`), a ordem de que a fase 2 do gate precisa; nunca bloqueia, tem tempo limitado, silencioso em erros | — (hook) |
| `aiwp-project-state.sh` | Imprime se cada projeto e POC é um projeto do workspace: o marcador na linha 1 do `README.md` dele (da `developer`, lido com `git show`) contra o `VERSION` e o `migrations/`: sem marcador, em dia, desatualizado com as migrações pendentes, ou o próprio repositório do workspace; e se um hotfix na `main` ainda não foi mesclado na `developer` (a partir das refs de rastreamento remoto, sem fetch). Só leitura; usado pelo hook, pelo `aiwp-cmds.sh open`, pelo gate e pelo `/normalize-projects` | `bash scripts/aiwp-project-state.sh billing-api` |
| `init-repo.sh` | Cria um projeto em `projects/` como repositório git independente, ou uma POC (`custom/pocs/`) ou uma ferramenta sua (`custom/tools/`) na camada custom, com o README de um projeto ou POC começando pelo marcador da versão do workspace; nunca escreve no core. Nunca sobrescreve | `bash scripts/init-repo.sh --type project --name billing-api` |
| `sync-env.sh` | Cria ou completa o `.env` preenchido a partir do `.env.example` de uma pasta, mostrando só os nomes das chaves: `custom/env/<name>.env` (modo 600) para `docker`, `docker/sonar` e `tools/<name>`, acrescentando `env/` ao `custom/.gitignore` quando falta; `<dir>/.env` para um projeto ou clone. Por trás do `/local-env` | `bash scripts/sync-env.sh --path docker` |
| `run-tools.sh` (+ `run-tools.py`) | As ferramentas locais: `list --json` e `status` mostram as ferramentas desta máquina (as ferramentas de contêiner de `tools/compose.yaml`, com o bloco `x-run-tools` de cada uma, e o console de contêineres desta máquina: docker-ce no Linux e no WSL, Colima no macOS), o estado delas e o que impede cada uma de iniciar (configuração faltando em `custom/`, ou na pasta que `AIWP_CUSTOM_DIR` indica; uma porta ocupada); `up` recusa essas, marca as imagens que substitui como `rollback-latest`, move uma ferramenta que ainda está no projeto compose antigo para o grupo `claude-cli-agents-tools` (copiando um volume nomeado, mantendo o antigo) e inicia o resto com `docker compose up -d --build --wait`, ou o serviço do console; `down` só para. Por trás do `/run-tools` | `bash scripts/run-tools.sh up observability` |
| `agent-copy.py` | A cópia Docker de uma tarefa, por trás de `up`, `down`, `status`, `close` do `aiwp-cmds.sh` e do merge do gate: escreve o arquivo de override de uma cópia (imagens próprias, sem nomes fixos, portas livres aleatórias em 61000-65535), lista os grupos `agent_` e destrói um grupo só pelo label do compose e só quando o nome dele casa com `^agent_[0-9]{4}-[a-z0-9][a-z0-9-]*$` | `python3 -I scripts/agent-copy.py list` |
| `lib/env.sh` | Biblioteca: onde mora o `.env` preenchido de uma pasta do core e qual arquivo o compose lê com `--env-file`. Carregada por `sync-env.sh`, `sonar.sh` e `validate.sh` | — |
| `lib/projects.sh` | Biblioteca: o layout de `projects/` (qual pasta é repositório). Carregada por `init-repo.sh`, `history.sh`, `aiwp-project-state.sh` e `aiwp-gate.sh` | — |

## Testes

Cada suíte roda sozinha, em pastas descartáveis: `bash scripts/tests/<name>/test-<name>.sh`. Os testes Python (`scripts/tests/test_*.py`) rodam sob o gate de cobertura: `bash scripts/validate.sh --only coverage`.

| Suíte | Cobre |
| --- | --- |
| `tests/check-workspace/` | `check-workspace.sh`, o ledger, e o tratamento de argumentos e o check de segredo rastreado do `validate.sh` |
| `tests/aiwp-cmds/`, `tests/test_agent_copy.py` | `aiwp-cmds.sh` e `agent-copy.py`: clones, push automático, recusas do pre-push, hook Stop, close, a cópia da tarefa (`up`, `down`, `status`, destruição por label) com um docker falso e, quando o Docker e o `alpine:3.20` estão na máquina, uma cópia real ao lado de uma stack final que ela nunca toca; `deploy` e `rollback` |
| `tests/aiwp-gate/` | `aiwp-gate.sh`: as duas fases do gate, o `/merge` da pessoa de que a fase 2 precisa dentro do Claude Code (o alvo dele, o limite de 12 horas), os grupos de cópia destruídos depois do merge, base que andou, conflitos, a auditoria, release (uma `main` protegida e o pull request dela, os casos de `--tag`), o hotfix (a partir da `main`, para a `main`, a tag dele, o merge de volta, limpo e com conflito, e o repo bloqueado), apply, e os passos da normalização contra remotos bare locais: `developer`, as tags de checkpoint, `bring`, o gate que julga o que a branch acrescenta |
| `tests/guard-bash/`, `tests/test_guard_bash.py` | `guard-bash.sh` e `guard-bash.py` |
| `tests/guard-subagent-model/`, `tests/test_guard_subagent_model.py` | `guard-subagent-model.sh` e `guard-subagent-model.py` |
| `tests/setup-claude/`, `tests/test_rules_config.py` | `setup-claude.sh` e `rules-config.py` |
| `tests/aiwp/` | `aiwp.sh`, o `install.sh` da raiz e o `release-notice.sh`, offline, sobre um repositório de fixture com duas releases |
| `tests/sync-env/` | `sync-env.sh` e `lib/env.sh` |
